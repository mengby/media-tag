# 上传、人脸打码与视频变速实施补充

日期：2026-11-06。状态：专题设计；D09已实现[上传与衍生契约](upload-variants.md)，D10[人脸打码核心与复核接口](face-redaction.md)已实现，D11变速及D12页面尚未实现。依据用户新增需求：剪辑师上传素材，使用人脸打码和变速，并扩充相应素材库。

2026-11-07归并：当前范围与全项目顺序见 [需求基线](REQUIREMENTS.md) 和 [实施计划](IMPLEMENTATION_PLAN.md)，真实状态见 [进度记录](PROGRESS.md)。本专题负责视频处理/人员交互及D09～D12，不另维护一套项目进度。

## 1. 产品流程与首期范围

界面方向已由用户选定：**极简风格，素材库默认画廊、可切换列表；人脸打码和视频变速放进独立的“视频处理”功能；AI 打标签在后台自动进行。** 这次确定的是产品结构，D09上传/契约和D10打码核心已实现；人员页面、产品变速及组合处理仍为拟定。D10工程验证不等同于A04业务集和人工全片复查验收。

素材库与视频处理使用两个入口，共用上传、文件身份及版本记录：

```text
素材库 → 上传素材 → 完整性校验与原件登记 → 后台自动打标 → 人工审核队列
                                                   → 更新检索索引
视频处理 → 上传视频 / 从素材库选择 → 打码 / 变速 / 同时处理
                                    → 生成预览 → 复核 → 下载 / 加入素材库
                                                       → 后台更新技术属性与标签建议
```

首期支持批量上传、整段固定倍速、全部人脸打码、按画面中轨迹选择排除对象、手动补框和时间区间修正；分段变速和速度曲线后置。用户不需要填写素材技术字段，来源与原始页面可在上传时填写，也可暂留未核实。

上传完成后原件登记在当前权限范围内；需要打码的原件与未复核输出不自动进入团队可下载区。输出是否成为团队可用素材与“医学标签已确认”分别记录。处理完成表示有可复核文件，不等于隐私、许可或医学通过。

### 已确定的界面结构与拟定交互

- 一级导航使用“素材库”“视频处理”“我的任务”。上传素材是素材库页主按钮；我的上传作为素材库筛选项。剪辑端不设置“开始打标签”按钮或模型配置入口。
- 素材库默认画廊，同页提供画廊/列表切换；切换保留搜索、筛选、选中素材及版本，记住个人偏好。同一逻辑素材的多个版本折叠展示。
- 卡片只显示缩略图、名称、时长/类型及必要状态。详情展示连续预览、下载版本、标签和来源；完整表头放到管理/导出功能。素材详情可提供“送到视频处理”快捷跳转，处理参数与预览始终在独立页面完成。
- 视频处理可以直接上传视频，不要求先进入素材库或完成打标。也可以选择已有的有权版本。两项处理独立开关，可单独或组合执行；设置后提交任务、查看进度、预览复核，再下载或主动加入素材库。
- 工具页新上传的输入先登记为私有工作素材；下载结果不等于发布到共享素材库。点击“加入素材库”登记共享可见范围及版本关系，再自动安排标签任务。原件、处理预览和已发布版本分别授权，不能借此绕过原有隐私或许可约束。
- 处理页显示真实预览、源时长和预计输出时长。需要修正人脸轨迹时再展开轨迹、补框和时间区间控制；速度默认 1.0，音频默认同步变速并尽量保持音调。状态使用“排队中 / 处理中 / 待预览确认 / 可下载 / 失败”，失败给出原因和重试入口。
- “我的任务”按上传与处理任务组织，后台标签只显示简短的“分析中 / 待审核 / 已确认 / 分析失败”。打标失败不影响已获授权的文件浏览、视频处理和下载；只重试失败阶段，不让剪辑重新上传。
- 人工医学字段确认、词表维护和表格导出保留在有权限的管理审核入口。“后台打标”指自动生成建议，不代表自动确认医学标签；普通剪辑不必逐项填写完整表头，也不承担默认审核角色。
- 搜索优先使用已确认的有效标签；若展示 AI 候选命中，明确标记“待审核”。口语扩展继续遵守已发布词表与歧义处理规则，不能将搜索词写回正式医学标签。

### 拟定的 Router/Worker 调度调整

素材库上传完成后，由服务端事务记录素材和待分析事件；Router 派发既有探测、抽帧、OCR、CLIP 等阶段，Worker 回传建议，服务端发布状态与索引。重复事件按输入哈希、规则及模型版本幂等处理，重启不丢任务。

视频处理提交独立任务，依赖文件校验、技术探测与处理配方，不依赖术语匹配、OCR 或语义打标签成功。Router 按配方只派发需要的 face_track、transform_render、output_validate 阶段；打码输出仍经 privacy_review 后才进入已处理副本下载入口。加入素材库时再触发需要的技术信息更新、标签继承或重新分析。

交互处理和后台打标使用分别可观察的队列；共用同一个 GPU 资源配额，不按队列各启动一个重模型。用户主动处理优先调度，同时保留后台任务公平性；只在阶段安全边界让出资源，不中途杀死正在写文件的渲染。任务刷新、取消、重试及过期结果拒绝沿用原协议。

## 2. 人脸打码：从检测扩展为完整视频处理

不需要生成式大模型。使用轻量检测器 + 跨帧跟踪 + 遮罩渲染。此前用于打标的稀疏抽帧检测不足以直接承担全视频打码，必须增加专用链路。

1. 解码所选完整区间，在源时间轴上检测人脸；首期优先逐帧检测并结合轨迹关联，性能实测不足再引入有覆盖验证的检测间隔策略。
2. 为每条轨迹记录 track_id、源帧时间、坐标、置信度与状态。不做身份识别，不建立人脸身份库。画面切换时重新初始化，不把上一个场景的框带到下一个场景。
3. 默认处理全部检测到的人脸；需要保留医生脸时，用户在预览中选择具体轨迹排除。不能凭站位、服装或模型猜测“谁是医生”。新出现的人脸仍默认纳入打码。
4. 遮罩覆盖整个人脸区域，按配置扩边，做轨迹平滑并限制在画面内；平滑不能导致快速移动时遮罩滞后。支持马赛克、模糊、实心遮挡，先提供马赛克与实心遮挡，强度通过实际画面验收。
5. 轨迹丢失、遮挡后重现、侧脸、出入画、快速运动和多人交叉列为复查片段；可在合理短区间保守延续遮罩，不能无期限猜框，也不能静默漏掉疑似人脸。
6. 允许人工补框、改起止时间与合并/分开轨迹；修改轨迹或强度后生成新配方版本，旧复核失效。
7. 渲染后检查完整输出可解码、遮罩时间覆盖、帧数/时间映射，并展示连续预览。仅在输出上“检测不到脸”不能证明打码充分，需要人实际查看并确认后作为团队可用的已处理副本。

人脸打码不会自动处理姓名、病历号、声音或其他可识别内容；这些若需要处理应另建明确任务，界面不把“人脸打码完成”写成“完全匿名”。原件、未处理缩略图与人脸轨迹仅对有权用户可见；团队缩略图和预览必须由已处理输出生成，不能泄露原脸。

现有表头的“含人脸=已处理副本”只在该输出通过人脸处理复核后填写，不能填写“无”假装原画面不存在人脸；其标签状态仍可为 AI初稿。

## 3. 视频变速：独立于 AI 的确定性能力

使用 FFmpeg 调整视频时间戳和音频速度，通常无需模型。用户明确选择倍速；默认 1.0，不继承 doctor-video-automation 的 1.25 倍规则。

- 首期 UI 提供 0.5、0.75、1、1.25、1.5、2 倍及范围内自定义值，先限制 0.25～4 倍；该范围是产品起步建议，不是 FFmpeg 技术上限。
- 整段固定倍速 s：输出时长约为原时长 / s。比如 10 秒素材，0.5 倍约 20 秒，2 倍约 5 秒。实际端点按编码帧/音频时间基准验证。
- 原声默认同步变速并尽量保持音调，可选去掉音频；避免只改视频导致音画错位。无音频素材走纯视频分支，多音轨首期要求选定输出轨，不能静默丢弃或拼错。
- 视频用 setpts 对时间作缩放，音频用 atempo；较大倍率按需要串联适当区间的 atempo。起始音画偏移也按同一时间基准缩放，不能各轨简单独立归零而丢失原有同步关系。
- 慢放不默认启用 AI 补帧或运动插帧；原始帧率不足可能显得不流畅，允许预览后选择。医学动作/机制素材不擅自生成不存在的中间状态。
- 变速不会反转动作方向，不提供倒放作为“方向修正”。改变速度可能改变观看者对过程快慢的理解，内部保留处理记录，入片适用性仍须重新判断。

工具依据：[FFmpeg 官方滤镜文档](https://ffmpeg.org/ffmpeg-filters.html) 提供 setpts、atempo 与 minterpolate。具体滤镜组合、构建能力、编码质量和音画同步在实现时用真实样本验证。

同时打码和变速时：以原片时间坐标检测/跟踪，按同一时间映射将遮罩应用到输出帧，最后编码。建议一条处理图完成以避免重复有损编码；最终输出重新做遮罩覆盖检查。禁止先变速后直接套原时间轴遮罩。

## 4. 原件和衍生素材怎样入库

一个逻辑素材组下面保留多个文件版本，例如“原件”“打码版”“0.75倍打码版”。检索默认折叠同组版本，下载时选版本；有隐私要求的组默认只向普通使用者提供已复核打码版，不能在下载失败时回退未打码原件。

每个可下载衍生素材拥有独立 asset_id、blob SHA256、存储位置和下载入口，内部记录：

| 内部字段 | 用途 |
| --- | --- |
| root_asset_id / parent_asset_id | 追溯原件与直接来源，区分处理链 |
| source_sha256 / output_sha256 | 证明处理的输入与输出 |
| recipe / recipe_hash | 处理顺序、速度、音频策略、遮罩轨迹修订、编码参数、软件/模型版本 |
| time_map | 源片段到输出片段的时间关系，支持未来分段变速 |
| processing_status / privacy_review_status | 分开记录生成成功、待复核、复核完成或失败 |
| reviewer / reviewed_output_hash | 复核人、时间及绑定的具体输出，避免沿用旧批准 |
| tag_origin / revision | 区分继承的标签与重新观察得到的标签 |

这些先作为内部字段，不擅自增加用户表头。CSV/飞书中每个正式可检索变体可独立成行，使用新素材 ID、哈希、技术属性和下载链接；组关系由应用保存，后续需要飞书直接查看关系时再确认表头扩展。

可继承原件来源记录、用途主题候选，但必须保留出处；不会因处理变成“项目自有”。重新计算尺寸、时长、哈希、音频、预览等实际属性。遮罩可能挡住文字/主体，因此 OCR、画面描述和可用片段按影响范围复核。

原来标注的片段 [a,b] 在固定倍速 s 下映射为 [a/s,b/s]（源时间先归一到共同起点），再按真实输出边界校验；非整段变速使用分段 time_map。继承医学标签可以显示原件已确认的依据，但不自动将新输出整行标为已人工确认。

同一源内容、同一完整配方重复请求复用有效结果，避免重复入库；更改倍速从登记的源基准重新生成，不在上次变速输出上叠加。若用户特意选择衍生文件继续处理，必须解析其来源与配方，显式记录实际累计变换。上传本库衍生文件哈希命中时复用关系；外部视频没有可追溯历史时，不能声称知道它此前是否变过速。

## 5. Router / Worker 扩展

新增处理运行阶段：upload_finalize（新上传时）→ variant_plan → face_track（按需）→ transform_render → output_validate → privacy_review（打码时）→ register_variant。下载和加入素材库分别操作；后者触发后台 tag，export 由独立授权操作触发，不与处理提交捆绑。

- upload_finalize：断点上传完成后校验大小/哈希/实际格式，在暂存区解码检查，原子登记；不信任浏览器传来的文件名/格式。相同文件去重复用 blob，但保留上传者与来源记录。
- variant_plan：固定源版本、选定操作、目标速度和音轨；生成配方指纹和源时间映射草案。只生成用户选择的版本，不自动制造所有倍速组合。
- face_track：只产带证据的轨迹与风险区间，不直接宣布输出已脱敏。
- transform_render：执行遮罩/时间处理，只写任务产物；原件不可写。处理配方是白名单参数，不能传任意 FFmpeg shell 字符串。
- output_validate：完整解码和技术校验、时间映射/遮罩检查，失败只返修相关阶段。
- privacy_review：独立人工操作，绑定输出哈希与遮罩版本；确认后才进入团队已处理素材视图。
- register_variant：唯一服务端事务写入 lineage、文件位置与标签继承记录；失败不影响已有版本，取消任务的产物不自动发布。

沿用任务租约、旧结果拒绝、人工值保护和重试机制。GPU 推理与硬件编码统一纳入资源调度；首期 GPU 重任务串行，避免 NVENC 编码和 VLM 推理共同挤占显存。CPU 编码可作基线，硬件编码是否启用以 FFmpeg 构建与实机质量/速度测试决定。
