# 口语词与专业术语对应：词表＋小模型实施方案

日期：2026-11-06。路线：用户已选择“词表＋小模型”。状态：方案与任务卡已补充，尚未开发、发布词表或运行模型。

## 1. 目标与边界

让剪辑师用日常表达搜索按专业标签登记的素材，并帮助打标人员把不同表达关联到相同概念。保留用户原话与实际画面证据，不把检索匹配当作诊断，不自动增加医学分类选项。

第一期采用：**已审核词表精确匹配 → 文本小模型召回候选 → 上下文规则筛选 → 有歧义时选择/复核**。不要求生成式大模型，不先训练自有模型，也不为此引入 Elasticsearch 或独立向量数据库。

以下仅为规则设计示例，不是已发布医学词条：

| 表达 | 拟定行为 | 禁止推导 |
| --- | --- | --- |
| 鼻子不通气 | 候选关联“鼻塞”概念 | 自动推导为某种鼻炎 |
| 肚子疼 | 候选关联“腹痛”，保留部位上下文 | 自动推导具体疾病 |
| 血管堵了 | 召回阻塞相关概念并标记歧义 | 直接等同“血栓” |
| 消肿 | 保留“肿胀减轻”的变化方向 | 与肿胀加重等价扩展 |
| 像海绵一样胀起来 | 分开保存实际主体与比喻喻体 | 将海绵直接标成医学结构 |

## 2. 两种词表分开管理

现有 **分类词表 taxonomy** 决定哪些值能填入科室、器官、疾病等锁定字段；新增 **术语对应词表 lexicon** 决定用户的表达如何关联到概念。两者各有版本，发布别名不等于发布新的疾病标签。

| 数据 | 必需字段与含义 |
| --- | --- |
| 概念 concept | 不变的 concept_id、标准名称、类型（器官/症状/疾病/过程等）、定义、适用范围、可选中英文别名、对应 taxonomy 选项 ID |
| 表达映射 alias_mapping | 原表达、规范化表达、目标 concept_id、关系类型、科室/器官等上下文条件、来源与定位、审核状态 |
| 概念关系 relation | 起点/终点 ID、关系类型、方向、扩展是否允许；不能把相关关系自动闭包为同义词 |
| 发布 release | lexicon_version、绑定的 taxonomy_version、内容哈希、发布者、时间、变更清单、上一版本 |
| 素材概念关联 asset_concept | asset_id/版本、concept_id、建议或有效状态、依据与操作者；和素材原文本并存 |
| 反馈 feedback | 查询表达、候选、用户选择/纠正、来源类型、待处理状态；点击不是审核通过 |

关系至少区分：equivalent（等价）、contextual（有条件对应）、broader/narrower（上下位）、related（相关）、metaphor（比喻）。只有已审核且满足条件的等价映射默认参与同义词扩展；其余只用于分组候选或用户主动扩展，保留方向，不双向乱扩。

同一表达可对应多个概念，不能设“一个词唯一对应一个疾病”的数据库约束；冲突规则需显示适用条件。标准名改名保留 concept_id 与旧名；概念合并/拆分使用显式迁移映射，不复用退役 ID。

用户 `asset-index-template/` 继续本地保留且忽略 Git。词表运营数据、医生原话和反馈放 `data/terminology/` 等忽略目录；Git 保存结构、算法、文档和合成测试夹具，不把原模板或词表内容换目录提交。

## 3. 词表从哪里来、如何发布

先覆盖常用科室，建议从实际授权使用的素材标签、口播稿和人工搜索表达整理首批 100～300 条候选映射。数量是起步规模建议，不代表已收集到数据。

每条候选保留来源、具体原句/位置与关系理由。标准名称优先对齐用户已发布的分类选项；外部术语资源记录出处与实际允许使用范围，不把网上语料自动当正式规则。

流程为 draft → review → published / rejected；只有指定词表管理人能发布。管理人审核“两个表达是否对应、在什么上下文成立、能否用于搜索扩展”，不是批准素材医学内容。模型、点击日志及自动导入只能形成候选。

发布前检查：空目标/失效 ID、未发布分类引用、重复或冲突映射、上下位环、错误方向、缺来源、未审核项。服务端产不可变快照和差异清单，支持回滚。别名变化只更新查询侧词表/文本向量，不要求全库重新抽帧或跑 VLM；概念语义改变时列出受影响素材，重新审核关联，不直接覆盖原标签。

## 4. 小模型方案

基线候选为 `BAAI/bge-small-zh-v1.5`，负责**文本到文本**候选检索；CLIP 继续负责图文匹配，二者向量空间不能混用。词表概念文档由标准名称、定义、已发布别名与适用范围构成，预计算向量；模型相似度只表示候选排序，不等于医学等价概率。

部署优先 CPU、常驻小词表向量；在 i5-14400F 上实测延迟后决定是否使用 GPU。若使用 RTX 5060，仍领取全局 GPU 槽，不和 VLM/编码无预算争抢。固定模型修订、分词器、编码规则、向量维度与归一化方式。

第一期向量存本地文件、元数据存 SQLite，少量概念直接矩阵检索。模型替换或概念文档变化需要重建对应文本索引；打包词表快照、模型配置和向量索引，通过校验后原子切换版本，避免新词表配旧向量。

参考依据：

- [BGE 官方模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)：提供中文语义检索能力，并说明阈值需结合实际数据选择。该模型是通用文本检索模型，未经本项目医学词对验证。
- [CBLUE / CHIP-CDN](https://github.com/CBLUEbenchmark/CBLUE)：可借鉴术语标准化的“召回＋排序”方法；它面向临床诊断表达，不是覆盖全部中文口语的成品词表。
- [Elastic 官方同义词文档](https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms)：可借鉴等价/单向映射与搜索时扩展。此处采用其设计思路，不新增 Elasticsearch 部署依赖。

## 5. 查询与打标的两条路径

### 查询时

1. 保留原查询；对 Unicode、空白及标点做受控规范化。否定、程度、部位、左右侧、时间和变化方向不能被清洗掉；拼写纠错只提候选，不能静默改医学名词。
2. 用发布词表匹配短语与上下文。优先最长合理短语，同时保存重叠/嵌套候选，不因子串命中就丢弃整句含义。
3. 命中唯一、已发布、上下文条件满足的等价映射，则生成概念检索；始终保留原文检索分支。不唯一时列候选，不强制取第一名。
4. 没有明确命中时，用 BGE 在已发布概念中取 top-k（起步 k=10，可配置），结合字段类型、原查询词项、上下文条件过滤与排序。模型只提候选，不自动写入永久别名表。
5. 明确的概念、否定与过程方向分别保留。“没有鼻塞”“鼻塞缓解”“鼻塞加重”不得归成相同检索意图。上下文解析不确定时返回 ambiguous，不盲目套硬过滤。
6. 基于概念关联和关键词召回素材；等价命中、字面命中、模型候选分层排序。可选图文检索分支只作补充，不将 BGE 分数与 CLIP 分数直接相加。
7. 页面显示“按哪个概念找到”以及可切换候选；状态分为 resolved、ambiguous、no_match、degraded。模型故障时保留词表与原文搜索，明确降级，不把故障写成无匹配。

上文规则用于素材检索，不承担临床诊断。正文是否真正支持某一医学概念，仍以实际素材及人工复核为准。

### 打标时

术语 Worker 可规范化 OCR/模型建议/人工输入中的概念表达，但必须带 evidence_origin。来源类型区分画面文字、模型视觉描述、人工输入、旧文件名与曾用原话。

旧文件名或用户搜索词只能帮助找候选，不能单独证明素材包含该疾病。Worker 只产生 concept 建议；医学字段仍逐条人工确认，人工有效值不被模型或词表更新覆盖。

现有表头不增加列：专业字段继续使用发布 taxonomy 选项；“中文检索词/英文检索词”可增加经确认的有限别名，保留人工编辑。导出不展开无限同义词，不把临时模型候选写入正式词条。应用的 concept_id/映射依据存在内部表。

飞书原生搜索不会自动执行本项目的语义 Worker。首期在自有检索入口提供完整口语搜索，飞书使用导出的有限检索词；要在飞书内直接调用完整检索，后续另做入口集成，不能宣称仅同步数据就已实现。

## 6. Router / Worker 协议

运行流程：query/tag_request → terminology_resolve → asset_search / tag_candidate → user_selection / review（按需）。词表维护单独走 collect_candidate → human_review → release_build → publish；发布只能由服务端处理。

| 职责 | 输入 | 输出与权限 |
| --- | --- | --- |
| terminology_resolve Worker | 原文、用途 search/tag、上下文、来源证据、固定词表/分类/模型/索引版本 | 原文片段、概念候选、关系、命中路径、原始分数、方向/否定、歧义；只读发布词表，无标签写入/词表发布权 |
| asset_search Worker/服务模块 | 确认或候选概念、词项、方向约束、调用者权限 | 按权限筛选的素材/片段及命中理由，不返回无权访问的原件或衍生文件 |
| lexicon_build Worker | 已审核修订集合、基准 release、发布配置 | 候选快照、向量文件、校验报告和哈希；无切换线上版本权限 |
| 唯一服务端 | 人工审核/发布请求、Worker 结果、基准版本 | 校验冲突后发布或采用；写审计、失效对应缓存，不修改其他人工标签 |

任务包沿用主方案的 task_id、job_id、attempt、lease_epoch、输入指纹、产物和错误协议；额外包含 request_kind、context、evidence_origin、lexicon_version、taxonomy_version、embedding_index_version、model_revision、target_fields。查询请求不得附任意 shell 或任意文件路径。

缓存包含原文与规范化版本、上下文、词表/模型/索引版本；素材搜索缓存另含可见范围与索引修订，不能跨用户复用私有结果。词表切换后旧查询可按绑定版本返回并标识，旧打标候选采用前须重验当前分类/素材版本。

交互查询设置短超时，超时走明确降级；不排在长视频渲染后无限等待。词表构建等后台任务沿用租约和有限重试。运行日志保留定位所需信息，对查询原话按权限保存，不把用户文本提交 Git。

## 8. 实施顺序与验收目标

并入现有主线：D00/D01 → D13 → D14（同时需 D03）→ D15（同时需 D06）→ D16 → D07 总体验收。可与上传/打码/变速开发分支并行；合并接口和 GPU 资源仍统一管理。可选 VLM、飞书/OSS保持后置。

首批候选词表人工审核后发布 v1，再运行对照试点。建议准备至少 100 条独立查询，覆盖等价表达、多义词、未收录词、否定、左右侧、方向相反、比喻和不相关内容；先冻结标注，再分校准/验收集，近义改写和同源句按组划分，避免泄漏。

零容忍的程序约束：未审核映射不可发布、查询不能写正式标签、无权限素材不可返回、模型故障不得伪装为无匹配。拟定业务目标：在独立验收集上，明确解析的概念准确率至少 95%，同时报告解析覆盖率；方向和错误疾病扩展逐例复核，未达标缩小自动解析范围并显示候选。目标不是当前性能承诺，小样本结果不能代表全医学领域可靠性。

一期不做领域微调。待积累足够真实纠正数据、证明词表＋通用模型的瓶颈后，另评估文本重排模型或微调，不将其作为首期依赖。
